# 負荷対策と保存基盤の再設計 — 設計書

作成日: 2026-08-02 ／ 状態: **本番反映まで完了（2026-08-03）**

## 実装結果（あとから追記）

全4段を実装。E2E 97件すべて成功（`node tools/e2e.mjs`）。

| | 着手前 | 実装後 |
|---|---|---|
| 100人同時の依頼確認 | 失敗率 約95%（試算） | **全員成功・285ms（実測）** |
| 100人同時の面談申請 | 同上 | **全員成功・447ms（実測）** |
| store JSON（保存のたびに全読み書き） | 4.00MB | **1.04MB（74%削減）** |
| 1リクエストのヒープ | 約4.8MB × 同時数 | 約1.2MB（全体で1つ・キャッシュ） |

設計との差分：
- **リトライ増の応急処置は不採用**。効果を測ったところ20人同時で57%→39%にしか下がらず、
  処理能力の不足であって回数の問題ではないと判明したため
- 代わりに**サーバー内キャッシュ**を追加（設計時には気づいていなかった。読み込み経路の
  改善効果が大きく、約20行で全リクエストが軽くなる）
- 通知は「一斉に押される操作」ではないが、依頼・面談と同じ保存に相乗りしていたため
  一緒にテーブル化した
- `POST /api/notifications` を追加（面談・イベント側の通知が専用APIに移った分の受け皿）

## 1. 目的と背景

- 想定規模：登録500人・**同時アクセス100人**（ユーザー指定。依頼の一斉確認・締切前の面談申請・イベント出欠が集中源）
- 制約：**料金が発生する方法は禁止**。Render無料プラン＋Turso無料枠のまま達成する
- 2026-08-02の調査（本物のサーバーを起動したE2Eテスト）で、負荷以前の**重大バグ2件**も発覚したため、修正を第0段として本計画に含める

### 実測値（判断の根拠）

| 項目 | 値 | 測定方法 |
|---|---|---|
| 500人・1年運用時のstore JSON | 約5MB | 想定件数（面談3,000・メール9,000・通知3,000・イベント500）で合成 |
| PUT /api/db 1回のCPU | 30ms（フルコア）→ 約300ms（Render 0.1コア換算） | parse+merge+validate+stringifyを実測 |
| 保存の処理能力 | **約3件/秒** | 上記より |
| 同時保存の失敗率（現状） | 20人:57% ／ 50人:88% ／ 100人:95% | 待ち行列シミュレーション（10秒分散） |
| リトライ8回化のみの効果 | 20人:39%（不十分） | 同上。**回数でなく処理能力の問題** |
| 専用API化後 | **全条件で0%** | ロック競合が存在しなくなるため |
| readDB 1回のヒープ | 4.8MB（PUTは3面保持で約15MB） | `--expose-gc` で実測。512MBでは同時30台強で枯渇 |
| 役割別の配信サイズ | インターン生100KB／スタッフ172KB／admin 5MB | `scopeDBForUser` 通過後を実測 |

## 2. 対象範囲と非対象

**対象**：`server/server.js` の保存基盤、`index.html` の書き込みが集中する5操作の呼び出し部。

**非対象（YAGNI）**：
- ホスティング移行（Supabase/Firebase）— 設計問題は移行では解決せず、書き直しリスクだけ増える
- `branches` / `events` / `availability` / `profiles` / `internships` のテーブル化 — 低頻度でstore JSONのままで足りる
- 低頻度な残り約20操作の専用API化 — 409リトライで十分
- フロントの読み込み経路 — `GET /api/db` が組み立て済みオブジェクトを返す形を維持し、画面側は原則無改修

## 3. 目標アーキテクチャ

データの置き場所を「書き込み頻度」で二分する。

| 置き場所 | データ | 理由 |
|---|---|---|
| **正規テーブル**（新設） | requests / request_reads / event_responses / interviews / notifications / emails | 一斉書き込みが起きる。行単位で書けばロック競合が消える |
| **store JSON**（現行のまま） | branches / events / availability / profiles / internships | 低頻度。楽観ロック＋リトライで足りる |
| 正規テーブル（既存） | users / sessions / google_tokens / password_resets | 変更なし |

読み込みは `GET /api/db` がテーブル＋storeを**1つのオブジェクトに組み立てて返す**。フロントの `DB.requests` 等の参照は今のまま動く。

書き込みだけが変わる：集中5操作は専用APIへ、残りは従来どおり `PUT /api/db`（ただしテーブル化した項目はPUT側で無視する）。

## 4. 第0段：バグ修正（最優先・フロント変更なし）

### 確認済みバグ

1. **データ消失**：f847413（7/30）で `requests` / `profiles` / `internships` を追加した際、前日実装の `mergeScoped()`（server.js:553）の許可リストが未更新。**admin以外の保存でこの3項目が黙って消える**（APIは200を返す）。依頼機能はadmin以外では実質最初から動いていない
2. **情報漏えい**：`scopeDBForUser()` が `requests` を絞り込まず、**全支部の依頼本文が全ユーザーに配信される**

### 修正仕様

コードから確定させた現行の権限仕様に合わせる：

**requests**（送信=staff/branch_admin、宛先は送信時に `recipient_ids` で固定、削除機能なし）
- 配信（scope）：`sender_id === 自分` または `recipient_ids` に自分が含まれるものだけ。adminは全件
- 保存（merge）：自分が送信者の新規追加と、自分の `read_by` 追記だけを取り込む
- 検証（validate）：新規は `sender_id === 自分` かつ staff系のみ。既存行は `read_by` への自分の追記以外の変更を拒否。削除拒否

**profiles**（departments・internship_id。自分で編集＋staff系が同支部インターン生の internship_id を代理設定）
- 配信：同支部のユーザー分のみ（adminは全件）
- 保存：自分の分＋（staff系なら）同支部メンバーの分だけ取り込む
- 検証：インターン生は自分以外の変更を拒否

**internships**（支部ごとのマスタ。staff系が管理）
- 配信：同支部のみ
- 保存：staff系のみ、`branch_id === 自分の支部` の行だけ取り込む
- 検証：インターン生の変更を全拒否。削除時は登録者ゼロをサーバー側でも確認（現在はフロントのみのガード）

### 受け入れ条件

今回作ったE2Eテスト（§9）で「消えた」「見える」が全て「残る」「見えない」に変わること。

## 5. 第1段：サーバー内キャッシュ＋書き込み直列化

- `readDB()` の結果をプロセス内に1個保持し、`writeDB()` 成功時に更新する。Tursoへの読みは起動時と書き込み失敗時のみ
- 効果：全リクエストから「Turso往復＋5MB parse」が消える。ヒープも共有1個＋役割別の絞り込みコピー（約200KB）だけになる
- **直列化**：`readDB → 変更 → writeDB` の区間をpromiseチェーンのミューテックスで1本化する。既存の `/api/mail/send`（1396–1403行）は現状この区間に競合バグがあり（同時送信で片方のログが消える）、これも同時に解消される
- **キャッシュ破壊の防止**：`readDB()` の戻り値を書き換えている3箇所（server.js:159, 1397–1398, 1736–1755）を「複製してから変更→writeDB→キャッシュ差し替え」に統一する
- 前提：Render無料プランは常に1インスタンス。複数インスタンス化する場合はこの設計を見直すこと（コメントとして明記する）

## 6. 第2段：集中5操作のテーブル分離＋専用API

### テーブル定義

```sql
CREATE TABLE requests (
  id TEXT PRIMARY KEY, sender_id TEXT NOT NULL, branch_id TEXT NOT NULL,
  subject TEXT NOT NULL, body TEXT, target_label TEXT,
  recipient_ids TEXT NOT NULL,        -- JSON配列。宛先は送信時固定なので正規化しない
  created_at TEXT NOT NULL
);
CREATE TABLE request_reads (          -- read_by配列を行に分解。300人の一斉確認が行INSERTになる
  request_id TEXT NOT NULL, user_id TEXT NOT NULL, read_at TEXT NOT NULL,
  PRIMARY KEY (request_id, user_id)
);
CREATE TABLE event_responses (
  id TEXT PRIMARY KEY, event_id TEXT NOT NULL, user_id TEXT NOT NULL,
  response TEXT NOT NULL, updated_at TEXT NOT NULL,
  UNIQUE (event_id, user_id)
);
CREATE TABLE interviews (
  id TEXT PRIMARY KEY, intern_id TEXT NOT NULL, staff_id TEXT,
  branch_id TEXT, status TEXT NOT NULL,
  data TEXT NOT NULL,                 -- 希望日時等の可変部はJSONのまま（形が固まっていないため）
  created_at TEXT NOT NULL, updated_at TEXT NOT NULL
);
CREATE TABLE notifications (
  id TEXT PRIMARY KEY, type TEXT, msg TEXT, branch_id TEXT, at TEXT NOT NULL
);
CREATE TABLE emails (
  id TEXT PRIMARY KEY, sender_id TEXT, receiver_id TEXT,
  subject TEXT, body TEXT, sent_at TEXT NOT NULL, delivered INTEGER
);
```

### 専用API

| API | 置き換える操作 | 概要 |
|---|---|---|
| `POST /api/requests` | submitRequest() | 依頼作成＋宛先分の通知INSERT。staff系のみ |
| `POST /api/requests/:id/read` | confirmRequest() | `request_reads` に1行INSERT（冪等） |
| `PUT /api/events/:id/response` | vote() | UPSERT。同じ回答の再送信で削除（現行仕様の踏襲） |
| `POST /api/interviews` | submitApply() | 申請。`status='applied'`、本人のみ |
| `PATCH /api/interviews/:id` | confirmInterview() / failInterview() / reopenInterview() | 状態遷移。staff系のみ。確定時のGoogleカレンダー連携（`syncInterviewsToGoogle`）はここへ移す |

各APIは触る行だけを読み書きし、storeの楽観ロックを一切通らない。**同時100人でも失敗率0%**（§1の根拠）。

### 移行

- 起動時に一度だけ：storeに旧項目が残っていれば行に展開してテーブルへINSERTし、storeから該当キーを除去（マイグレーション済みフラグをstoreに持つ）
- `GET /api/db`：テーブルから読んで従来のキー名（`requests`＝read_by合成済み、`event_responses`、`interviews`、`notifications`、`emails`）でstore由来の項目と合成して返す。**フロントの読みは無改修**
- `PUT /api/db`：テーブル化した項目はbodyから除去して無視（古いキャッシュを持つタブからの上書き防止）
- `validateDiff()` から該当セクションを削除

### 段階的な出し方

1コミット1コレクションで進める（各段で全E2Eを回す）：
1. requests＋request_reads＋notifications（最も危険な一斉確認を先に）
2. event_responses
3. interviews（Google連携の移設を含むため最後・最重量）
4. emails（サーバー内だけの変更）

### フロント変更

- 該当5操作の `mutate(db=>{...})` を `api()` 呼び出しに置換し、成功後にローカルの `DB` を同じ形に更新して `render()`（画面の見た目・楽観更新の体感は不変）
- `test/test-mock.js` に新APIのモックを追加（`node tools/make-test-page.mjs` で再生成）

### 10.1 データの退避（実装済み）

退避は2重にしてある。**どちらか片方でも残っていれば元に戻せる。**

**(A) サーバー側の自動退避 — 手を動かさなくても必ず走る**

`migrateStoreToTables()` は、store から項目を消す前に `backupStore()` で
store 行の原本を **`store_backup` テーブル**へそのまま複製する。
接続情報を用意する必要がなく、デプロイすれば自動的に行われる。
ここで失敗した場合は例外が上まで伝わり、引っ越しそのものが行われない。

**(B) 手元へのダンプ — デプロイ前に人が実行する**

```powershell
$env:TURSO_DATABASE_URL = "libsql://..."   # Render → Environment から取得
$env:TURSO_AUTH_TOKEN   = "..."
node tools/backup-turso.mjs
```

`_backup/turso-YYYYMMDD-HHMM.json` に全テーブルが保存される。読むだけで書き込まない。

> **`_backup/` は gitignore 済み。** 全員分のメールアドレスとパスワードのハッシュが
> 入るため、publicリポジトリに載せると全員の情報が公開される。絶対にコミットしないこと。

### 10.2 元に戻す手順

引っ越し後に問題が起きた場合、store を引っ越し前の状態へ戻す。

```sql
-- 1. 何が退避されているか確認する
SELECT id, reason, taken_at, length(data) FROM store_backup ORDER BY id;

-- 2. 戻す（id は上で確認したもの）
UPDATE store
   SET data = (SELECT data FROM store_backup WHERE id = ?),
       updated_at = (SELECT updated_at FROM store_backup WHERE id = ?)
 WHERE id = 1;
```

戻した store には `movedToTablesV1` の印が無いため、**次回起動時に引っ越しが再び走る**。
再実行させたくない場合は、コードを戻したうえで実施すること。
なお引っ越しは `INSERT OR IGNORE` なので、再度走っても二重登録にはならない。

## 11. リスクと対策

| リスク | 対策 |
|---|---|
| マイグレーションで本番storeを壊す | 事前退避（§10）＋一回性フラグ＋E2Eでの移行テスト |
| キャッシュとTursoの不整合 | 書き込み成功時のみキャッシュ更新。失敗時はキャッシュ破棄して再読込 |
| 第2段のフロント置換で画面が壊れる | 1コレクションずつ・都度ブラウザ回帰。`mutate()` 自体は残すので他画面に影響しない |
| 0.1コア換算・シミュレーションが実態とずれる | 数値は「設計判断の根拠」であり保証値ではない。第2段完了後にローカル同時50接続で実測（§9） |
