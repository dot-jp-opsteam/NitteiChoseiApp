# Google登録者がメールアドレスでもログインできるようにする

作成日: 2026-08-03

## 背景

Googleでログインしてアカウントを作った人は、以降「Googleでログイン」からしか入れない。
ログイン画面の「メールアドレスでログイン」に同じGmailアドレスを打っても弾かれる。

原因は `server/server.js` の作りにある。Googleで新規作成されたユーザーは
`password_hash` が空のまま保存される（`server.js:1341`）。
`/api/auth/login` はその状態を検知して 401 を返す（`server.js:1229`）。

## 大前提（技術的な制約）

**Googleアカウントのパスワードを、このアプリのログイン欄で使うことはできない。**
OAuth / OpenID Connect でGoogleから受け取れるのはメールアドレス・本人確認済みフラグ・
表示名・アイコンだけで、パスワードは渡されない。これはGoogleに限らずどのサービスでも同じ。

したがって「メール欄からもログインしたい」を叶える唯一の道は、
**このアプリ専用のパスワードを別途設定してもらうこと**である。
本設計は、その設定を迷わず行える導線を用意することを目的とする。

## すでに動いているもの

調査の結果、サーバー側の機能はほぼ揃っていた。

- `/api/auth/forgot-password` は `password_hash` が空のユーザーにも再設定メールを送る
  （`findUserByEmail` と `status === 'active'` しか見ていない / `server.js:1480`）
- `/api/auth/reset-password` は `password_hash` を無条件に UPDATE する（`server.js:1526`）
- ログイン後の設定画面には「パスワードを設定」が既にある（`index.html:1139`）
- 本番はメール送信が有効（`/api/auth/config` が `passwordReset: true` を返す）

つまり **今でもパスワードは設定できる**。足りないのは、
ログイン画面で困っている人がそこへ辿り着く導線と、原因が分かるエラー文だけ。

## 方針

ログイン画面でメール＋パスワードが弾かれたその場で解決させる。
ログイン後に促す方式（設定画面のバナー等）は、困っている本人が
ログイン画面から先へ進めていないため採らない。

## 変更内容

### 1. サーバー: エラー応答に種別を付ける（`server/server.js:1229`）

Googleのみ登録のユーザーに対する 401 のボディに `code: 'google_only'` を足す。
フロントがこの分岐を出し分けるための識別子で、文言の文字列一致に頼らないための措置。
`code` はメール送信の有効・無効にかかわらず常に返す。

文言は、次に何をすればよいかが分かる内容へ変える。
メール送信が無効な環境（`mail.MAIL_ENABLED === false`）では設定メールを送れないため、
その場合の文言は従来どおり「Googleでログインしてください」とする。

`code` を返すのはこの分岐のみ。パスワード不一致・ユーザー不存在の 401 は
現状のまま区別のつかない同一メッセージを返す（どちらか一方を特定させないため）。

### 2. フロント: ログイン画面に設定導線を出す（`index.html:956` `doLoginAuth`）

`data.code === 'google_only'` を受けたとき、エラー欄の下に案内ブロックを描画する。
「パスワードを設定するメールを送る」ボタンは `PASSWORD_RESET_AVAILABLE` が真のときだけ出す
（既存の「パスワードをお忘れの方」リンクと同じ判定 / `index.html:835`）。
偽のときは「Googleでログイン」だけを出す。

```
✗ このアカウントはGoogleで登録されています。
  メールでログインしたい場合は、このアプリ専用の
  パスワードを設定してください。

  [ パスワードを設定するメールを送る ]
  [ Googleでログイン ]
```

- 「パスワードを設定するメールを送る」… ログイン欄に入力済みのアドレスで
  `/api/auth/forgot-password` を呼ぶ。押下後はボタンを戻さず「送信しました」に変え、
  連打による多重送信を防ぐ（既存 `doForgotPassword` と同じ扱い / `index.html:870`）。
- 「Googleでログイン」… 既存のGoogleログイン導線をそのまま呼ぶ。

送信処理は `doForgotPassword` と重複するため、
メールアドレスを引数に取り送信結果を返す共通関数へ切り出し、両方から呼ぶ。
これにより送信済みフラグの扱いが1か所にまとまる。

### 3. メール文面（`server/mail.js:101` `sendPasswordResetMail`）

現在の件名・本文は「再設定」を前提にしている（`パスワード再設定のご案内` /
`パスワードの再設定を受け付けました。`）。
初めて設定する人が受け取ると噛み合わないため、どちらの状況でも読める文言に直す。
メールの種類は増やさず、既存の1関数の文言だけを調整する。

## 変更後の挙動

- パスワード設定後は、メールログインとGoogleログインの**両方**が使える。
  `google_sub` は消さないため、Google側の紐付けは維持される。
- `reset-password` は既存仕様として全セッションを削除する（`server.js:1535`）。
  そのためパスワード設定直後は一度ログインし直しになる。この挙動は変更しない。
- 既存のパスワード持ちユーザーの動作は一切変わらない。

## セキュリティ上の判断

「このアカウントはGoogleで登録されています」と返す以上、
アドレスを打つだけでそのアドレスが登録済みかどうかを外部から判別できる。
これは現行コードでも既にそうなっている。社内向けの業務アプリであり
影響が小さいこと、原因が分かることの価値が上回ることから、現状の挙動を維持する。

## テスト（`tools/e2e.mjs` に追加）

`setupDB` に `password_hash` が空のユーザー（Googleのみ登録相当）を1件追加し、次を検証する。

1. そのアドレス＋任意のパスワードで `/api/auth/login` を叩くと
   401 かつ `code: 'google_only'` が返る
2. テストから `password_resets` に有効なトークンを直接挿入し、
   `/api/auth/reset-password` でパスワードを設定できる
3. 設定後、メール＋そのパスワードで `/api/auth/login` が成功する
4. 既存のパスワード持ちユーザーのログインが従来どおり成功する（退行の確認）

`/api/auth/forgot-password` 自体はe2eの対象外とする。
e2eではSMTPの環境変数を設定しないため `MAIL_ENABLED` が false になり、
このエンドポイントは 503 を返して実際の送信経路を通らないため。
メール送信を含む確認は、本番相当の環境で手動で行う。

## 対象外

- パスワードレスログイン（メールを打つと自動でGoogleへ飛ばす方式）
- ログイン後のバナー等による設定の催促
- 認証以外のリファクタリング
