# 面談まわりの改善 設計書

作成日：2026-08-06

## 0. この文書であつかうこと

面談の申請（インターン生側）と、面談の確定（スタッフ側）について、6つの改善をまとめて行う。

1. 希望時間の範囲表示を直す
2. 申請画面に、選び方の説明を足す
3. 面談申請の通知を、再読み込みなしで届ける
4. その通知で画面が暗転しないようにする
5. スタッフの時間選択をアコーディオンにする
6. 希望順を「第1希望」と色で見せる

対象ファイルは `apply.html` / `index.html` / `style.css` / `server/server.js`。

## 1. 希望時間の範囲表示

### 1.1 いまの状態

表の1行は「その時刻から30分の枠」を表す。17:00・17:30・18:00 の3行を選ぶと合計90分になるので、
`fmtRanges()`（apply.html）と `fmtGroupRange()`（index.html）は「17:00〜18:30」と出す。

計算としては正しいが、申請するインターン生は「17:00から18:00までを選んだ」と受け取るため、
出てくる表示と食い違って見える。

### 1.2 新しい規則

**続いた枠のまとまりについて、範囲の終わり＝最後の枠の開始時刻。ただし枠が1つだけのときは開始＋30分。**

| 選んだ枠 | いま | 変更後 |
|---|---|---|
| 17:00 / 17:30 / 18:00 | 17:00〜18:30 | **17:00〜18:00** |
| 20:00 / 20:30 / 21:00 / 21:30 | 20:00〜22:00 | **20:00〜21:30** |
| 17:00 のみ | 17:00〜17:30 | 17:00〜17:30（変わらず） |

### 1.3 直す場所

- `apply.html` の `fmtRanges(list)`
- `index.html` の `fmtGroupRange(g)`

どちらも「続いた枠の run を作り、`hm(先頭)〜hm(末尾+30分)`」という同じ形をしている。
この末尾の出し方だけを次の規則に差し替える。

```
run.length > 1 ? hm(run[末尾]) : hm(run[0] + 30分)
```

離れた区間を `＆` でつなぐ扱いは変えない。区間ごとにこの規則を当てる。

### 1.4 承知しておく副作用

面談そのものは30分なので、「20:00〜21:30」と出ている希望で 21:30 開始を選ぶと、
実際の終了は 22:00 になる。表示の終了時刻と実際の終了時刻は一致しない。

これは 2026-08-06 にユーザーの判断で受け入れた。
選べる開始時刻は減らさない（21:30 開始は今までどおり選べる）。

## 3. 面談申請のリアルタイム通知

### 3.1 いまの不具合と原因

スタッフの画面は、面談申請が届いても再読み込みするまで気づけない。

原因は `index.html:483` の定期ポーリング。

```js
const remote = await apiGetDB();
if (remote && remote.updatedAt && remote.updatedAt !== DB.updatedAt) { ... }
```

`updatedAt` は `store` テーブル（1行JSON）が書き換わったときだけ変わる。
ところが面談と通知は**専用テーブル**に入るため `updatedAt` は動かない。
したがって条件が永久に成立せず、30秒ごとに取りに行っているのに一度も反映されない。

これは 2026-08-02 の保存基盤の再設計で専用テーブルへ移したときの取りこぼし。

### 3.2 方式：SSE（サーバー送信イベント）

サーバーが変化を検知した時点で、つながっている画面へ押し出す。

**認証の制約**：このアプリはセッションを `Authorization: Bearer` ヘッダだけで持ち、
Cookie を意図的に使わない（`server/auth.js` の冒頭に理由あり。タブごとに別アカウントで
ログインできるようにするため）。

ブラウザ標準の `EventSource` はカスタムヘッダを付けられないため、そのままでは使えない。
検討して**不採用にした案**：

- トークンを `?token=` でURLに載せる → Render のアクセスログにセッショントークンが残る。却下
- 短命チケットを発行する → `EventSource` の自動再接続は同じURLを叩くので、チケットが失効して再接続できない。却下

**採用**：`fetch()` のレスポンスを `ReadableStream` として読む自前のSSEクライアント。
`Authorization` ヘッダを付けられる。再接続は自前で書く。

### 3.3 サーバー側

**新設：`GET /api/stream`（`requireAuth`）**

```
Content-Type: text/event-stream
Cache-Control: no-cache
Connection: keep-alive
X-Accel-Buffering: no      ← 中間のバッファリングを止める
```

- つながった接続を、**支部IDごと**の集合として持つ（`Map<branch_id, Set<res>>`）。
  通知（`notifications`）はもともと支部単位で積まれ、支部の全員が見るため。
- `res.on('close')` で集合から外す。
- **25秒ごとにハートビート**（`:ping\n\n`）を送る。Render の前段が無反応の接続を切るため。
- プロセス内のメモリに持つ。Render 無料プランはインスタンスが1つなので成立する
  （`readDB()` のキャッシュと同じ前提。インスタンスを増やすときは作り直しが必要）。

**送る内容**

```
event: refresh
data: {"kinds":["interview","notification"]}
```

中身はきっかけの種類だけ。データ本体は載せない。載せると権限ごとの絞り込みを
配信側でもう一度書くことになり、`/api/db` の判定と二重管理になるため。
受け取った画面が `/api/db` を取り直す。

**押し出す場所**

いま `insertNotification()` を呼んでいる箇所すべての直後。具体的には：

- `POST /api/apply/:token`（面談申請）
- `PATCH /api/interviews/:id`（面談確定・不成立・申請中に戻す）
- `POST /api/notifications`（画面から積む通知。依頼・イベント）
- `POST /api/requests` ほか、通知を伴う操作

取りこぼしを防ぐため、`insertNotification()` の**中**から呼ぶ。
呼び出し側を1つずつ直すと、あとで足した通知で忘れる。

配信の失敗は握りつぶす（本筋の保存は成功しているため）。

### 3.4 画面側

- ログイン後に接続を開き、ログアウト時に閉じる。
- 受け取ったら `apiGetDB()` で取り直し、**静かに反映**（第4節）。
- 切れたら再接続。1秒 → 2秒 → 4秒 …と延ばし、上限30秒。タブが隠れている間は接続を保つ。
- **既存の30秒ポーリングは残す**。SSEが張れていないときの保険。
  ただし判定を直し、`updatedAt` だけでなく**面談・通知の件数と最終更新も見る**ようにする
  （3.1 の不具合そのものの修正。SSEが動かない環境でも最大30秒で追いつく）。

### 3.5 Render での注意

- SSE の接続が張られている間、インスタンスはスリープしない。
  無料プランの稼働時間は 750時間/月、31日を丸ごと常時起動しても約730時間なので収まる。
  実際にはスタッフがアプリを開いている間だけなので、これよりずっと少ない。
  むしろ「開かない」問題が軽くなる副次的な利点がある。
- **⚠️ 750時間は無料サービス全体の合計**。いまは1サービスなので問題ないが、
  **無料サービスをもう1つ増やすと合計が750時間を超え、月末に止まる**。
  サービスを増やすときは、この設計が常時起動を招いていることを思い出すこと。
  追加の課金は一切ない（外部サービスもnpm依存の追加もなく、Node標準機能だけで書ける）。
- `server/` を触るので Build Filters の条件は満たす。

## 4. 暗転しない仕組み

### 4.1 原因

`render()`（index.html:1478）は最後に `bindReveal(m)` を呼ぶ。
`bindReveal()` は画面内のすべての `.card` / `.hex` に `.reveal` を付ける。
`.reveal` は「透明＋下にずらす」初期状態で、IntersectionObserver が見つけてから `.in` を付けて現れる。

つまり**再描画のたびに画面の中身がいったん消え、フェードで戻る**。
これが「画面全体が一瞬真っ暗になる」の正体。人の操作で画面を切り替えるときは演出として働くが、
背景の更新でこれが起きると、読んでいる途中で画面が消えることになる。

### 4.2 直し方

**`renderQuiet()` を足す。** `render()` と同じ内容を描いたうえで、

- `bindReveal()` を呼ばない
- 代わりに `.card` / `.hex` へ直接 `.reveal .in` を付ける（初期状態を通らないのでフェードしない）

背景からの更新はすべて `renderQuiet()` を通す。人が押した操作は今までどおり `render()`。

### 4.3 描き直さない条件

次のときは再描画そのものを見送り、**ベルのバッジ更新とトーストだけ**にする。

- シートが開いている（`#scrim.open`）── 面談の詳細を見ている最中に消えると操作できない
- 入力中（`document.activeElement` が `input` / `textarea` / `select`）── 打ちかけが消える

なお、なぞって選ぶ処理（`APDRAG` / `SELDRAG`）は `apply.html` にしかない。
`index.html` の旧・面談申請画面は 2026-08-06 に撤去済みで、
`apply.html` はログインしないためこの通知の仕組みとは無関係。判定に含めなくてよい。

見送ったときは「あとで反映する」印を立て、シートを閉じた時点・入力から離れた時点で
`renderQuiet()` を走らせる。

### 4.4 知らせ方

- ベルのバッジ（`updateBell()`）を更新する
- トーストで「新しい面談申請が届きました」と一度だけ出す
- 画面全体を覆うものは一切出さない

## 5. スタッフの時間選択（アコーディオン）

### 5.1 いまの状態

`openInterview()` の `choiceGroup(n, g)` が、希望ごとに見出しと**開始時刻のボタンを最初から全部**並べる。
幅のある希望や「終日OK」の日は、20:00〜／20:30〜…と何個も並び、
希望が3件あると画面が時刻ボタンで埋まって、どの希望を見ているのか分からなくなる。

### 5.2 変更後

```
┌────────────────────────────────┐
│ 第1希望  8/7(金) 20:00〜21:30      ▾│   ← 既定は閉じている
├────────────────────────────────┤
│ [20:00〜][20:30〜][21:00〜][21:30〜] │   ← 押すと下に開く
│ この中から開始時刻を選んで確定します       │
└────────────────────────────────┘
│ 第2希望  8/8(土) 14:00〜16:00      ▸│
```

- 見出し（`.chead`）全体が開閉ボタン。右端に山形の印を置き、開くと回る。
- **30分1枠だけの希望は今までどおり1行**（`choiceRow`）＋「これで確定」。開く中身がないため。
- ~~確定済みの日時を含む希望は最初から開く~~ → **取り下げた**（2026-08-06、実装中に判明）。
  この仕組みは成立しない。理由は2つ。
  1. 面談が `fixed` のとき、`openInterview()` は希望の一覧（`choiceGroup`）そのものを描かず、
     確定日時を出す別の分岐に入る。開く対象の画面が出てこない
  2. 面談が `applied` のときは、`PATCH /api/interviews/:id` が `status!=='fixed'` の場合に
     `confirmed_datetime` を必ず `null` にする（`server/server.js` 2545行付近）。
     新規申請時も `null`。つまり「申請中なのに確定日時が入っている」状態はサーバー側で作られない

  設計時にサーバーの状態遷移を確かめきれていなかった。**アコーディオンは常に閉じた状態で開く。**

### 5.3 開閉の持ち方

`openInterview()` はシートを組み立て直す作りなので、開閉の状態を画面の外に持つ必要がある。

```js
let IV_OPEN = new Set();   // 開いている希望の番号。面談を開き直すと空にする
```

`openInterview(id)` の先頭で、直前に開いていた面談と違えば `IV_OPEN` を作り直す。
このとき、確定済みの日時を含む希望の番号だけを最初から入れておく（5.2 の「確定済みは開く」はこれで実現する）。
開閉は `IV_OPEN` を書き換えて `openInterview(id)` を呼び直す
（シートの中だけなので、第4節の暗転の話とは別系統）。

### 5.4 CSS（style.css）

- `.cgroup .chead{cursor:pointer; …}` と山形の印
- `.cgroup:not(.open) .cslots, .cgroup:not(.open) .cnote{display:none}`
- 開閉のアニメーションは付けない（高さが変わる要素の transition は中身の量で速さが変わり、かえって落ち着かない）

## 6. 希望順の表示と色

### 6.1 変更後

`1` `2` `3` という数字を、**`第1希望` `第2希望` `第3希望`** に変える。

色は**申請画面の一覧とまったく同じ**にする。インターン生が申請時に見た色と、
スタッフが確定時に見る色を揃えるため。既存の CSS 変数をそのまま使う。

| 順位 | 背景 | 文字 |
|---|---|---|
| 第1希望 | `--bad-soft` | `--rank1`（赤系） |
| 第2希望 | `--rank2-soft` | `--rank2`（黄系） |
| 第3希望 | `--ok-soft` | `--rank3`（緑系） |
| 第4希望以降 | `--warn-soft` | `--warn` |

第4希望以降の色は、申請画面の `.selsummary .sr .cn`（style.css 741行）の既定値に合わせる。
スタッフ画面のいまの既定（`--brand-soft` / `--brand-d`）とは違うが、
「インターン生とスタッフで同じ見え方にする」ほうを優先する。

### 6.2 直す場所

- `index.html`：`choiceRow(n, val)` と `choiceGroup(n, g)` の `<span class="cn">${n}</span>` を
  `<span class="cn r1">第1希望</span>` の形にする。順位のクラスは `apply.html` と同じ
  `rankOnly(n) = 'r' + Math.min(n, 4)` の規則で付ける。
- `style.css`：`.choice .cn` と `.cgroup .chead .cn` を、22px の正方形から
  文字が入るラベル型（`padding` 指定）に変え、`.r1` / `.r2` / `.r3` の色を足す。
  741〜745行の `.selsummary .sr .cn` と同じ値を使う。

## 9. 気をつけること

- `server/slots.js` の枠の作り方は**変えない**。変えるのは表示の文字だけ
- `index.html` の `DEFAULT_WEEKLY` と `server/slots.js` の `DEFAULT_WEEKLY` は同じ値に揃えること（今回は触らない）
