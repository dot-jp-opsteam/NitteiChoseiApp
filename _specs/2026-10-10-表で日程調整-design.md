# 表で日程調整（Tappy相当）— 設計

2026-10-10。チャットで機能の構成を承認済み。この文書は実装前のレビュー対象。

## 目的とユーザーが決めたこと

OPSスタッフが自由な表を作成し、共有URLから複数人の空き時間を集める。
授業の空きコマだけでなく、一般の会議・イベントの日程調整にも使える。

- 「作成・管理はOPSスタッフ、回答は誰でもできる」。回答にログインを求めない。
- 「URLを知る人は全員の名前と集計を見られる（Tappyと同じ）」。選択したマスの参加者と、各人の空き時間も公開する。
- インターン生向けの機能は今後も追加・拡張する。CLAUDE.mdの旧スタッフ専用方針は更新済み。
- テンプレート、自由な行・列名、タップ・なぞり入力、本人専用リンクでの再編集、人数による色分け、メンバー絞り込みを入れる。
- 既存アプリの緑系配色とライト・ダークテーマに合わせる。無料の既存基盤で動かす。
- 「表で日程調整」を独立した機能として追加する構成を承認済み。

## 調査したTappyと構成の判断

2026-10-10に公式サイトをブラウザで確認した。

- http://tap-py.com/ : 登録不要、表による日程調整、タップ入力、人数の濃淡表示、マスごとの参加者表示。
- http://tap-py.com/create : 時間割・カレンダーのテンプレート、昼休み・土日・コマ数、開始日・日数・時刻、自由な縦横の項目、プレビュー。
- http://tap-py.com/usage : 時間割や午前・午後の表、メンバー名を押して集計対象を切り替える操作。
- http://tap-py.com/faq : 1イベント100人まで。原サービスの無更新1か月での自動削除は、この機能では採用しない。

既存のfree.htmlとfreeslot_requestsは、スタッフの受付時間から作った日時枠を収集する仕組み。
一般の文字ラベルを持つ表を同じデータに混ぜると、時刻計算と意味が衝突する。
独立したテーブルと小さなモジュールを追加し、ログイン・DB・回数制限・共通CSSを再利用する。
予約・面談の確定やGoogleカレンダー登録は行わない。ここで扱うのは参加できるマスの収集と集計。

## 画面と操作

### スタッフの一覧・作成・管理

- staff、branch_admin、adminに「表で日程調整」の入口を用意する。表示するのは自分が作成した表。
- 一覧には件名、回答人数、受付中／受付停止、作成日を表示する。
- 作成欄は件名、説明、テンプレート、行・列の編集、表のプレビュー。共有URLを作成後に表示・コピーできる。
- テンプレートは「日付×時間」「曜日×コマ」「自由な表」。保存する表の形式はすべて共通。
- 日付×時間：開始日と日数、開始・終了時刻、30分／1時間の間隔。初期値は今日から7日・9〜17時・1時間。
  列は日付、行は時間帯。終了時刻は最後の時間帯の終わりとし、端数が出る設定は入力時に知らせる。
- 曜日×コマ：月〜金・5コマが初期値。土日、昼休み、コマ数1〜10を選べる。
- テンプレート適用後も行・列の名前を変更し、項目の追加・並べ替え・取り除きを行える。
- 集計はスタッフ側にも表示し、表の編集と受付停止・再開を行える。
- 受付停止中も公開URLで集計は見られるが、新規回答と再編集の保存は受け付けない。

### 共有URLの回答・集計

- 公開ページは /t/<32桁hex>。件名、説明、集計表、回答者、回答の入口を表示する。
- 名前を必須、コメントを任意で入力し、空いているマスを選ぶ。メールアドレスやアカウントは不要。
- 1回のタップで選択を反転。なぞる場合は最初のマスの反転後の状態を通過するマスへ適用する。
  同じマスを往復しても再反転しない。タッチは押したままの移動で選択し、表の外では通常のスクロールができる。
- キーボードでも各マスを選択できる。選択中の状態を色だけでなく記号とaria属性で伝える。
- 表全体を横スクロールでき、行・列の見出しを固定する。スマホで列を潰して文字を切らない。
- 全マス未選択でも「今回は参加できる時間がありません」として回答を送れる。
- 保存できるまで入力を保持し、送信中はボタンを無効にする。
- 送信成功後、本人専用の編集リンクを表示し、端末にも控える。本人の回答を読み戻して修正できる。
  初回送信時に編集リンクを控える案内を出す。リンク・端末の控えを両方失った場合は名前だけで編集させない。
- URLから閲覧できる名前・選択マス・コメントは回答フォームの送信前に明示する。
- 公開ページは開いた時、回答後、再読み込みボタン、タブに戻った時に最新の表を取得する。
  常時ポーリングや新しい外部サービスは追加しない。

### 集計

- 各マスに参加可能人数を表示し、集計対象人数に対する割合で濃淡を付ける。
- 0人のマスと未回答のマスを区別できるよう、詳細には参加できる人・参加できない人・未回答の人を分ける。
- マスを選ぶと名前一覧を表示する。名前を選ぶとその人の空き時間も確認できる。
- メンバーのチェックで集計対象を切り替える。初期値は全員。全員へ戻す操作を用意する。
- 絞り込みはその閲覧者だけの表示設定。保存された回答や他の閲覧者の表示を変えない。
- 全員を外した時は「集計対象を選んでください」と表示し、0人の結果を最適候補と呼ばない。
- 最大人数のマスを強調する。同数ならすべて強調し、全マス0人なら強調しない。
- 同じ名前でも別の回答IDなら別人として保存・集計し、表示には受付順の補助番号を添える。

## 表の編集と回答の整合性

- 行と列は位置や表示名ではなく、不変のIDで識別する。マスIDは行IDと列IDの組で決まる。
- 名前変更・並べ替えでは既存の回答をそのまま保つ。日付名を変えても自動的に別日へ移し替えない。
- 新しい行・列のマスは、既存回答者について「未回答」とする。「参加できない」に変換しない。
- 項目を取り除く操作は非表示にする。既存の回答データを消さず、集計対象から外す。
- テンプレートから表を作り直せるのは初回保存前だけ。保存後は安定した行・列IDを使って編集する。
- 表の更新と回答の保存にはrevisionを使う。画面を開いた後に表が変わっていれば409を返し、入力を保持して再読込を案内する。
- 回答の同時編集は回答自身のrevisionで判定し、後から古い画面が新しい回答を上書きしない。

## 保存するデータ

既存のlibSQLクライアントを使う。DBのstore、users、既存の日程調整のテーブルは流用して上書きしない。

### tally_boards

- id TEXT PRIMARY KEY : 内部ID。
- staff_id TEXT NOT NULL : 作成者。staff_idの一覧用インデックス。
- token TEXT UNIQUE NOT NULL : 共有URL用の乱数32桁hex。
- active INTEGER NOT NULL DEFAULT 1 : 回答受付の可否。
- data TEXT NOT NULL : JSON {title, description, template, rows:[{id,label,active}], columns:[{id,label,active}]}。
- revision INTEGER NOT NULL DEFAULT 1 : 表の更新ごとに増加。
- created_at / updated_at TEXT NOT NULL : ISO日時。

### tally_responses

- id TEXT PRIMARY KEY、board_id TEXT NOT NULL。board_idの読み出し用インデックス。
- name TEXT NOT NULL、note TEXT NOT NULL DEFAULT ''。
- data TEXT NOT NULL : JSON {selected:[マスID], answered:[マスID]}。
  answeredは送信時の有効な全マス、selectedはその中の参加できるマス。新しく追加されたマスはansweredに含まれず未回答と判断できる。
- edit_token_hash TEXT UNIQUE NOT NULL : 本人編集用の乱数48桁hexのSHA-256。生の編集トークンは新規保存の応答でのみ渡す。
- submission_key TEXT NOT NULL : 初回送信の再試行を識別する乱数。UNIQUE(board_id, submission_key)。
- revision INTEGER NOT NULL DEFAULT 1、created_at / updated_at TEXT NOT NULL。
- 同名の回答を上書きする制約は付けない。

初回送信の再試行では同じsubmission_keyと編集トークンを送り、両方が一致する時だけ同じ回答を返す。
ブラウザで安全な乱数の編集トークンを事前生成し、成功確認まで保持する。応答喪失で回答が二重に作られない。
表のrevision確認、人数上限、新規挿入／回答更新は同じ書き込みトランザクションで処理する。
回答の保存は全有効マスを対象とし、古い画面から取り除かれたマスを再登録することを防ぐ。

## APIとアクセス

| メソッド・パス | 内容 |
|---|---|
| GET /api/tally-boards | 自分の表の一覧 |
| POST /api/tally-boards | 表を新規作成 |
| GET /api/tally-boards/:id | 所有する表と公開可能な回答 |
| PUT /api/tally-boards/:id | revisionを指定して表・説明・受付状態を更新 |
| GET /api/tally/:token | 公開の表・回答・revision。停止中も閲覧可能 |
| POST /api/tally/:token/responses | 名前・コメント・selected・表revision・submission_key・編集トークンで新規回答 |
| GET /api/tally/manage/:editToken | 編集トークンで本人の回答・回答revision・現在の表を取得 |
| PUT /api/tally/manage/:editToken | 本人の回答を表revision・回答revision付きで更新 |

- スタッフAPIにはrequireAuthとstaff／branch_admin／adminのロール確認、作成者本人の所有権確認を付ける。
- 他人の表を内部IDで指定した時も404とする。共有URLの閲覧権限を管理権限へ昇格させない。
- 公開GETはlimitPublicRead、公開POST／PUTはlimitPublicWriteを付ける。
- 共有トークンと編集トークンは長さとhex形式を検査する。存在しない編集トークンは404。
- 公開APIに編集トークン／ハッシュ、submission_key、staff_id、スタッフのメールアドレスを含めない。
- 共有URLには回答者名・選択マス・コメントだけを公開する。編集APIも他人の編集情報を返さない。
- 本人編集のページは既存予約と同じ /t/manage/<token> とする。
  公開ページ・編集ページはReferrer-Policy: no-referrer、APIはCache-Control: no-store。ログに本文や編集トークンを出さない。
- 表示名・説明・コメントは文字列として扱い、HTMLを必ずエスケープする。

## 初版の上限と初期値（設計上の前提）

- 1スタッフ30表、1表100回答、最大31列・48行。非表示にした項目を含めたID総数もこの上限内。
- 件名100文字、説明2000文字、行・列名40文字、回答者名80文字、コメント500文字。
- 有効な行と列はそれぞれ最低1つ。空の見出し、重複ID、存在しないマス、過大な配列を保存時に拒否する。
- 全マス未選択の回答を許可し、その人も回答人数・集計対象人数に含める。
- 上限に達しても既存回答の再編集はできる。受付停止は新規・再編集の両方を停止する。
- 自動削除、メール通知、Googleカレンダーとの自動連携、一般利用者による表の作成は初版の対象外。

## 検証と受け入れ条件

- テンプレート、行・列の追加と並べ替え、重複名と安定したID、人数の集計、同数の最適候補、対象0人を純粋関数で確認。
- 既存回答のある表で名前変更・項目追加・非表示を行っても、別のマスへ回答がずれないこと。
- スタッフ作成→URL→ログインなしで2人以上が回答→集計と絞り込み→本人リンクで再編集を実APIと画面で確認。
- 同名回答者が別人として残ること。名前だけで他人を編集できないこと。未知・別人のトークンや他スタッフのIDを拒否すること。
- 非公開の編集トークン等が公開APIに出ないこと。受付停止・再開、revision競合、同時の上限超過、送信再試行を確認。
- PCと幅390px／320pxでライト・ダークの表示、横スクロール、タッチ・キーボード入力を確認する。
- 指定の既存テストと追加したtallyのテストを実行してからmainへpushする。
- Renderで公開されたコミットと新規URLの配信を確認する。
