# 表で日程調整 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** OPSスタッフが自由な表を作り、誰でも共有URLから空き時間を回答・閲覧・集計できる機能を追加する。

**Architecture:** 既存の面談・予約・空き時間収集とは独立した表と回答のテーブルを追加する。純粋なモデル、保存API、共通の表描画・入力、スタッフ画面、公開ページに分ける。認証、libSQL、回数制限、テーマ変数は既存のものを利用する。

**Tech Stack:** Node.js >=18、CommonJS／ブラウザJavaScript、Express、@libsql/client、HTML、CSS。新しい外部サービス・依存パッケージは不要。

**Spec:** [_specs/2026-10-10-表で日程調整-design.md](2026-10-10-表で日程調整-design.md)。設計書は2026-10-10にユーザーが承認済み。実装開始にはこの計画と実行方法の確認を受ける。

## Global Constraints

- 「作成・管理はOPSスタッフ、回答は誰でもできる」。回答にログインを求めない。
- 「URLを知る人は全員の名前と集計を見られる（Tappyと同じ）」。
- 既存アプリの緑系配色とライト・ダークテーマに合わせる。無料の既存基盤で動かす。
- 1スタッフ30表、1表100回答、最大31列・48行。非表示にした項目を含めたID総数もこの上限内。
- 件名100文字、説明2000文字、行・列名40文字、回答者名80文字、コメント500文字。
- 全マス未選択の回答を許可し、その人も回答人数・集計対象人数に含める。
- 自動削除、メール通知、Googleカレンダーとの自動連携、一般利用者による表の作成は初版の対象外。
- CSSはtly-接頭辞。既存の公開ページ・認証の権限・他画面の見た目を変更しない。
- ファイルを削除しない。一時DBも削除する処理を新しいテストへ追加しない。
- 既存ファイルは対象箇所だけ編集する。mainへのpushは指定テストをすべて通してから行う。

## Review Focus

- 応答が失われた初回送信の再試行：同じ鍵で同じ回答を返し、二重登録しない。Task 3で実API検査。
- 開いた画面より後に表や回答が変わった場合：409を返し、入力を保持して再読込できる。Task 3とTask 6で検査。
- 同名の回答者と他人の編集リンク：名前で紐付けず、自分のトークンで自分だけを修正する。Task 3で検査。
- 年末・うるう日・時間帯の端数：テンプレートは日付を正しく生成し、端数を黙って切り捨てない。Task 1で検査。
- 端末の保存領域が使えない・なぞり中にキャンセル：リンクを画面で控えられ、入力は意図せず反転しない。Task 4とTask 6で検査。

### データの形

- Config: `{title,description,template,rows:[{id,label,active}],columns:[{id,label,active}]}`。
- 行・列IDは英字から始まる64文字以内の英数字・ハイフン・アンダースコア。新規項目はr_またはc_に安全な乱数を付ける。
- マスIDは `rowId + ':' + columnId`。ラベル・順番をIDに使わない。
- 公開Board: `{token,active,revision,config}`。スタッフBoardはこれにid・url・created_at・updated_atを付ける。
- 公開Response: `{id,name,note,selected,answered,revision,created_at,updated_at}`。selectedとansweredはマスIDの配列。
- APIの入力キーはcamelCase、SQLの列名は設計書のsnake_caseで固定する。
- 正規化結果は `{ok:true,config}` または `{ok:false,code,error}`。回答の場合は成功値をdataに持つ。
- 409のcodeは `stale_board`、`stale_response`、`closed`、`limit`。入力不正は400、不存在・所有権違いは404。

## Task 1: 共通モデルと純粋関数のテスト

**Files:** Create server/tally.js、tools/test-tally.mjs。

**Interfaces:**
- `cellId(rowId,columnId) -> string`。
- `activeCells(config) -> string[]`。有効な行と列の積を行順・列順で返す。
- `makeTemplate(input,idFactory) -> {ok:true,config}|{ok:false,code,error}`。configには空のtitle・descriptionを含む。
  inputは `{kind:'calendar'|'timetable'|'custom',startDate,days,start,end,step,periods,lunch,weekend}`。
  idFactory(prefix)はr_／c_を受け取り一意のIDを返す。日付はUTC日付演算で進め、端末の時差でずらさない。
- `normalizeBoard(input,previous=null) -> {ok:true,config}|{ok:false,code,error}`。既存IDを保持し、入力から抜けた既存項目は非表示のまま補完する。
- `normalizeResponse(input,config) -> {ok:true,data}|{ok:false,code,error}`。dataは{name,note,selected,answered}。
  answeredはサーバー側のactiveCellsから作り、クライアント指定のansweredを信用しない。
- `tally(config,responses,selectedIds=null) -> {total,cells,best}`。
  cells[マスID]は `{count,yes:[回答ID],no:[回答ID],unknown:[回答ID]}`。bestは最大人数のマスID配列。
- `beginStroke(selected,cell) -> {selected,target,visited}`、`visitStroke(state,cell) -> 同じ形`。
  配列は元の入力を書き換えずに返す。targetは最初のマスで決めた追加／解除の真偽値。

## Task 3: 公開回答・本人編集・再試行と同時実行

**Files:** Modify server/tally-routes.js、tools/test-tally-e2e.mjs。

**Interfaces:**
- GET /api/tally/:token -> `{board,responses}`。BoardとResponseは共通インターフェースの公開形。
- POST /api/tally/:token/responses bodyは `{name,note,selected,boardRevision,submissionKey,editToken}`。
- GET /api/tally/manage/:editToken -> `{board,response}`。
- PUT /api/tally/manage/:editToken bodyは `{name,note,selected,boardRevision,responseRevision}`。
- 保存成功は `{responseId,responseRevision,boardRevision,editUrl}`。editUrlは入力からの編集トークンを使って構成する。
- shared token=32桁hex、editTokenとsubmissionKey=48桁hex。保存する編集トークンはSHA-256だけ。

## 実行方法

推奨は、このチャット内で同じ担当がTask 1〜7を順に実装し、最後に独立レビューを行う方式。
共通モデル・API・共通UIが互いのインターフェースに依存するため、同じ担当がつなぐと調整が少ない。
別案は、Taskごとに実装担当とレビュー担当を分ける方式。段階ごとに第三者確認が入るが、引き継ぎが増える。
計画内容と実行方法をユーザーが確認してから着手する。
